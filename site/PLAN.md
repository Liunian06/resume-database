# 介绍网站开发计划

## 目标

为 resume-database skill 做一个介绍性静态网站，作为小红书、抖音内容的落地页：不看代码的大学生也能在几屏内看懂这个工具做什么、怎么装。

风格：未来感，类似苹果官网的逐屏滚动宣传页，用 JS 和 canvas 动画演示功能。

## 当前状态

- 仓库目前是私有的，Pages 需要等仓库公开（或确认账号计划支持私有仓库 Pages）后才能部署
- 先在本地开发 `site/`，**不推送**。用户开放仓库权限后，再推送并接入部署
- 自动发版的 push 触发问题尚未查清（v1.0.6 的 release 未发出），部署联动应在它排查完之后再做

## 技术方案

- 纯原生 HTML、CSS、JS，不引入框架，不加构建步骤
- 逐屏效果：CSS 的 `position: sticky` 加 `IntersectionObserver`
- 动画：canvas 绘制
- 字体：使用系统字体，不使用 MiSans（LICENSE 中 MiSans 为小米独立协议，网页发布是否允许未核实）
- 示例数据：姓名、学校、经历全部虚构，不出现真实个人信息

### 双版本页面

- 同一个 URL、同一个入口 `index.html`，**不做跳转**到 `m.` 之类的地址
- 电脑版和手机版是两套独立的页面：DOM、样式、动画脚本互不共用，各自按设备特点设计
- 设备判断用 `matchMedia`，不读 UA：宽度足够大且有 hover 与精细指针（`(hover: hover) and (pointer: fine)`）算电脑，否则算手机。iPad 横屏、折叠屏按同一条件处理
- 首屏渲染前用一小段内联 CSS 隐藏不匹配的那一套，避免闪屏
- 只加载匹配那一套的脚本，手机不下载电脑版的 canvas 代码
- 监听 `matchMedia` 的 change 事件：旋转屏幕或拖动窗口跨过断点时切换，并销毁上一套的动画、释放 canvas
- **文案、版本号、更新日志、安装命令只维护一份**，放在 `content.js`，两套页面都从它渲染。构建时的版本注入也只改这一处
- **两套页面的屏数一致，内容一致**，差别只在布局、交互和动画的呈现方式

## 目录结构

```
site/
├── PLAN.md          # 本文件
├── index.html       # 唯一入口：设备判断、加载对应版本
├── content.js       # 全部文案与版本信息（两套页面共用）
├── desktop/
│   ├── desktop.css
│   └── desktop.js   # 电脑版布局与 canvas 动画
├── mobile/
│   ├── mobile.css
│   └── mobile.js    # 手机版布局与 canvas 动画
└── assets/          # 少量图片素材（如交流群二维码）
```

## 分屏规划

两套页面共用以下 7 屏，文案相同：

| 屏 | 内容 | 动画（呈现方式在两端分别设计） |
|----|------|------|
| 1 | 首屏：标题加一句话定位 | 粒子背景 |
| 2 | 痛点：一份简历投所有岗位 | 大量相同简历堆叠，突出千篇一律 |
| 3 | 核心流程：JD 到岗位画像到定制简历 | JD 解析为关键词，重组为定制简历 |
| 4 | 面试准备 | 问题卡片逐张浮现 |
| 5 | 投递追踪 | 表格中状态逐步推进 |
| 6 | 安装 | 安装命令，带一键复制按钮 |
| 7 | 版本与更新日志，交流群二维码 | 无或轻量 |

原则：每屏动画对应一个真实环节，不做纯装饰。炫技效果只放首屏。屏数固定为 7 屏，避免后期难以维护。

## 性能与可访问性

- 手机优先：流量主要来自小红书、抖音，多数在 App 内置浏览器打开，WebView 性能弱于系统浏览器
- 手机版 canvas 控制粒子数量与绘制复杂度；用 `navigator.hardwareConcurrency` 和帧率实测做降级，不靠 UA 识别环境
- 页面不在可视区时暂停动画
- 支持 `prefers-reduced-motion`：开启时关闭动画，显示静态内容
- 页面不依赖外部 CDN，国内访问不受影响

## 部署与发版联动（待仓库公开后做）

1. 仓库设置里把 Pages 的来源改为 GitHub Actions
2. 部署使用 `actions/upload-pages-artifact` 加 `actions/deploy-pages`，workflow 需 `pages: write` 和 `id-token: write` 权限
3. 部署写成 `release.yml` 里发版 job 之后的后续 job，不单独监听 release 事件。原因：用 `GITHUB_TOKEN` 创建的 release 不会触发其他以 release 为触发条件的 workflow
4. 构建时把 `SKILL.md` 的版本号、`CHANGELOG.md` 的更新记录注入 `content.js`，下载按钮指向最新 release 的 zip
5. `site/` 自身的改动（文案、截图）不会触发发版，部署需要另外监听 `site/**` 的推送
6. `.gitignore` 的白名单需新增 `!site/`

## 验证方式

两路分别验证，再验证切换：

- 电脑端：本地起静态服务，用预览工具在桌面尺寸下逐屏查看
- 手机端：用预览工具的 mobile 预设查看；注意它会模拟触屏，设备判断是否走手机分支也要确认
- 切换：在两种尺寸之间切换，确认旧版本动画已销毁、没有残留的 canvas 或定时器
- 检查控制台无报错、页面无外部请求
- 检查开启 `prefers-reduced-motion` 时的静态回退
- 检查两端的文案完全来自 `content.js`，没有各自硬编码
